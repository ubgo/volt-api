# Coding Standards

## General

* Target Go 1.25; run `gofmt`/`goimports` on save. Tabs for indentation.
* Keep packages lowercase, no underscores; exported identifiers in PascalCase, unexported in camelCase.
* Group imports: stdlib, third-party, local; avoid unused aliases.

## Functions & Error Handling

* Keep functions small; pass contexts explicitly. Avoid global state except singletons for infra clients.
* Return `error` as last value; wrap with context (`fmt.Errorf("action: %w", err)`); never panic in libraries.
* Prefer interfaces near consumers for testability; keep constructors simple (`NewX(cfg)`).

## DRY/SOLID

* Single responsibility per package; shared helpers live in `lace/` or clearly named subpackages.
* Avoid cyclic deps; depend on interfaces, not concretes (especially across modules).
* Reuse validation and middleware from `lace`/`saas/pkg` rather than re-rolling.

## Concurrency

* Respect context cancellation; avoid goroutine leaks. Protect shared state with channels or sync primitives.
* Use timeouts for external calls; make rate limits explicit.

## Testing

* Table-driven tests in `_test.go` adjacent to code. Favor fakes over network calls.
* Cover business logic, resolvers, and migrations; add regression tests for bugs.

## Database Connections

* **NEVER** create separate database connections with `ent.Open()` or `sql.Open()`.
* **ALWAYS** use `app.New()` to get the shared client: `plugins := app.New(); client := plugins.EntDB.Client()`
* This applies to: seed scripts, CLI commands, background workers, tests, and any code needing DB access.
* `app.New()` handles: config loading, ent runtime init, encryption keys, connection pooling.

## Generated Code

* **NEVER** edit files containing `Code generated by` comment at the top - these are auto-generated by scripts.
* Never edit generated files (`gen/`, `graph/generated`, PKL bindings). Regenerate via Taskfile targets and commit outputs together.
* Common generated file patterns: `*.gen.go`, `*_gen.go`, files in `gen/` directories.

## GraphQL Resolvers (gqlgen)

* **NEVER** create utility functions or helper files directly in the `resolver/` directory.
* The `resolver/` directory should **ONLY** contain resolver implementations and the `resolver.go` dependency injection file.
* Helper functions, utilities, and business logic should be placed in:
  * `internal/<package>/` for module-specific utilities (e.g., `internal/fileutil/`)
  * `lace/` for shared utilities across modules
  * `saas/pkg/` for saas-specific business logic
* This prevents gqlgen from moving/deleting helper code during regeneration.

## GraphQL File Uploads

* **ALWAYS** use base64-encoded content for file uploads in GraphQL mutations.
* **NEVER** use `graphql.Upload` multipart form uploads - they are complex for type-safe clients.
* Validate file type from **actual content** (magic bytes), not the filename extension.
* Example schema:
  ```graphql
  input FileUploadInput {
    fileName: String!   # Display name only
    content: String!    # Base64 encoded
  }
  ```
* Use `net/http.DetectContentType()` and magic bytes for file type validation.

## Cron Jobs

* **Maximum runtime**: No cron job should run longer than **12 hours**. System has 24h graceful shutdown timeout as buffer.
* Always use `gocron.WithSingletonMode(gocron.LimitModeReschedule)` to prevent overlapping runs.
* Jobs must be idempotent - safe to retry if interrupted.
* For long-running tasks, break into smaller batches with progress tracking.
* See `docs/incidents/2025-01-18-cron-graceful-shutdown.md` for graceful shutdown details.

## GitHub Secrets & Deployment

All secrets are defined in `.env.{env}` files (e.g., `.env.prod`, `.env.dev`).\
GitHub secrets are prefixed with `GITHUB_SECRET_` - the prefix is stripped when pushed to GitHub.

```bash
GITHUB_SECRET_VPS_HOST=192.168.1.1    # → GitHub secret: VPS_HOST                                                          
GITHUB_SECRET_CONTAINER_NAME=myapp    # → GitHub secret: CONTAINER_NAME                                                    
```

Key files are specified as a **JSON array** in `GITHUB_SECRET_KEY_FILES`:

```bash
# Single file                                                                                                              
GITHUB_SECRET_KEY_FILES=["mykey.pem"]                                                                                      
                                                                                                                           
# Multiple files (must be valid JSON with quoted strings)                                                                  
GITHUB_SECRET_KEY_FILES=["file1.pem", "file2.creds"]                                                                       
```

Key files must exist in the `_keys/` directory.\
Each environment gets its own workflow file: `deploy.{env}.yml`\
Branch mapping: `prod` → `main`, all others → same as env name.\
Commands:

```bash
go run ./scripts gh:secrets:update --env=prod   # Build secrets                                                            
go run ./scripts gh:secrets:push --env=prod     # Push to GitHub                                                           
go run ./scripts gh:env:setup --env=prod        # Full setup                                                               
```
