## 2. V2 mission framing

**Question:** we want pluggable, loosely coupled boilerplate. ORM and gqlgen
are tightly coupled, find the sweet spot.

**Decisions reached:**

- Accept compile-time coupling for ent, gqlgen, PKL Root.
- Decouple everything else: `app.Plugin` god struct → narrow `HostAPI`;
  features sprawl across 5+ dirs → feature-first `modules/<name>/`;
  monolithic main → self-registering modules.
- Phased rollout: define HostAPI + Module iface + pilot one feature, then
  measure pain delta before scaling.

**Artifact:** `MISSION_V2.md` written.

## 3. PKL strategy across modules

**Question:** can PKL config be imported from vendor directory or similar?

**Options weighed:**

- A — Root.pkl explicitly imports each module's PKL.
- B — Glob `import*("../../modules/*/config.pkl")` for auto-discovery.
- C — Per-module `pkl-gen-go` runs at module-author time, ships typed Go
  config struct alongside.
- D — Host configures via Go only, redeclares shape in own PKL.

**User constraint added:** "no host won't duplicate we need importability."
Eliminated D.

**Final pick:** Path 2 from a follow-up — `task pkl:link` symlink-stabilizes
paths via `go list -m -f '{{.Dir}}'`. Host imports module PKL via stable
`config/pkl/modules/<name>/Config.pkl` regardless of vendor / module-cache /
go.work-replace mode. Each module embeds PKL via `//go:embed` so files
survive `go mod vendor`. → ADR-V2-007.

## 5. Distribution model

**User stated:** "I want to be able to distribute and use in multiple
projects."

**Locked:** modules are separate Go modules with own repos

## 6. Contract repo (modkit)

**Chicken-and-egg problem:** module needs services from host (DB, logger);
host imports module. Direct module → host import is impossible because host
path varies (`github.com/anyone/their-app`).

**Solution:** interface-only package both sides import. `modkit` defines
`Services`, `Module`, registrar interfaces, tx helpers. ~300 LOC, near-zero
deps.

**Naming:** `modkit` chosen. Locked because renaming after publish breaks
every module ever shipped. → ADR-V2-003.

## 7. Cross-module joins (auth ↔ workspace ↔ roles)

**Question:** if each module owns its schema, how do JOINs work?

**Options:**

- Pattern 1: hard ent edges across modules (compile-time coupling).
- Pattern 2: soft FK by string ID, JOIN at service layer.
- Pattern 3: aggregate schemas at host codegen time (no Go imports between
  schemas; module schemas don't compile standalone).

**Pivot:** "host has its own ent client" idea was ruled out because module
runtime code can't import host's generated client (host path varies).

**Locked:** Pattern A revised — each module owns its own ent client
(`<module>/gen/ent/`), cross-module references use soft FK + service-layer
batch fetch (`GetMany`) + DataLoader at GraphQL boundary. → ADR-V2-006,
ADR-V2-008.

Optional: host MAY have its own aggregated ent client for cross-cutting
admin queries (read-only escape hatch). Module business logic never uses it.

## 8. Modules cannot import host

**User question:** "how the module will import the host generation ent
client functions like host.User.Query()?"

**Answer:** they cannot. The aggregated client at host is for HOST-level
queries only (reports, admin). Module business logic stays inside the
module's own ent client.

**Reinforced ADR-V2-006.**

## 9. No foundational tier

**Earlier draft proposed:** mod-iam owns User as foundational; other modules

**User pushed back:** "mod-iam does not suit — there could be many cases.

**Pivot:** drop foundational tier. Every module is a peer. Each ships own

## 10. Schema extension

**Question:** "how to have new fields to existing struct in the module — let
say I want to extend the User table?"

**Three patterns:**

- Pattern 1: sidecar table at host (typed, indexable, soft FK).
- Pattern 2: jsonb metadata column on module entity (loose, untyped).
- Pattern 3: fork module (last resort).

**Locked default:** every "extensible" module entity ships `metadata jsonb`
column + `Metadata` field on DTO (free insurance). For typed fields, host
adds sidecar in own dbent. Fork acknowledged as escape hatch. → ADR-V2-011.

## 11. Returning extra fields via API

**Question:** "how do we return extra fields if API is fixed in mod-auth?"

**Answer:** layered composition. Module API stays sealed; host owns
enrichment service.

- Internal Go: host's `users.Service.Get` returns `EnrichedUser{User, ...}`.
- GraphQL: `extend type User` in host schemas + field resolvers using
  DataLoader against sidecar.
- Other modules: caller passes enriched data as parameter, OR module declares
  provider iface (e.g. `ContactProvider`) and host implements it.
- **Forbidden:** module imports host's sidecar.

→ ADR-V2-012.

## 16. Configurable fields brainstorm

**Question:** "different consumers want different fields — phone unique, OR
no phone at all. How?"

**7 patterns weighed:**

| pattern | when | recommendation |
|---|---|---|
| metadata jsonb | ad-hoc loose data | use as default |
| config flags for behavior | validation rules on own data | use freely |
| capability modules (mod-auth-phone) | typed shared across consumers | use as primary tier |
| host sidecar table | app-specific typed fields | use when not shared |
| ent mixin injection at codegen | niche / one consumer | sometimes |
| multiple shipped variants (basic/full/enterprise) | never | never |
| fork module | structural mismatch only | never except last resort |

**Locked layered stack:**

- **Tier A — core:** mod-auth ships minimal {id, email unique, password,
  is_active, metadata}. No phone, MFA, OAuth.
- **Tier B — capability modules:** `mod-auth-phone`, `mod-auth-mfa`,
  `mod-auth-oauth`. Each owns its own table with own constraints. Soft FK
  to User by user_id.
- **Tier C — host sidecar:** for app-specific typed fields not shared.
- **Tier D — metadata jsonb:** loose escape hatch.

## 17. Module config scope rule

**User caught a sloppy answer:** "requirePhoneOnSignup. How? mod-auth has no
information about auth-phone."

**Correction made → new rule:**

> Module config validates only fields the module OWNS. Cross-module
> concerns are HOST orchestration.

mod-auth's config can set `minPasswordLength` (it owns password) but cannot
set `requirePhoneOnSignup` (phone is mod-auth-phone's data).

Composite signup logic lives in `saas/pkg/signup/service.go` — same
location pattern as `lifecycle/user_deletion.go`. Host knows which
capabilities are wired and enforces composite rules with its own config.

**This generalizes to a rule for the architecture:**

| concern | where | layer |
|---|---|---|
| field validation on own data | module Config + Writer impl | module |
| behavior toggle on own data | module Config | module |
| multi-module orchestration | host service | host |
| multi-module validation | host service | host |
| "required X" where X is another module's data | host service | host |
| module enforcing policy on caller across modules | wrong — host's job | banned |

## Cross-cutting themes that emerged

<Details summary="The single rule that keeps surfacing">

**A module never references another module's host or implementation.**

It references contracts (other module's `api/`) or pure interfaces from
modkit. Direction is always module → contract → host. Never module → host.

This rule produced:

- modkit (contract repo)
- per-module `api/` sub-packages
- soft FK across modules (no cross-module ent edges)
- module ents = own gen/ent
- Reader/Writer interfaces with `GetMany` for batching
- `clientForCtx` for tx-awareness
- Cascade hooks (`*By<Foreign>`)
- EnrichedUser at host
- signup orchestration at host
- module config scope rule

Once internalized, every architecture question answers itself.

</Details>

<Details summary="Why sidecar + metadata + capability modules coexist">

Three separate problems:

1. **One consumer's app-specific typed fields** → sidecar at host. Their app,
   their concern.
2. **Loose data anywhere** → metadata jsonb. Cheap default.
3. **Typed extensions multiple consumers want** → capability modules.
   Reusable, versioned independently.

These don't compete. Pick by axis: shared-vs-app-specific, typed-vs-loose.

</Details>

<Details summary="What V2 didn't try to fix">

- Multiple ent clients per app (still limited by ent's design)
- Cross-module SQL JOINs in business logic (deliberate trade for portability)
- Runtime module discovery / hot reload (Go is statically compiled — accept it)
- DI framework (wire/fx) — explicit constructor wiring is enough
- Schema-level customization at consume time (use composition instead)

</Details>

### 18. Extending Go structs from a module

**Question:** can mod-auth's `User` struct be extended (new fields) from
host?

**Answer:** Go has no struct inheritance. Closest mechanism is
**anonymous embedding**:

```go
type ExtendedUser struct {
    authapi.User              // anonymous: fields promoted, JSON flat
    Phone       string
    DateOfBirth time.Time
    Timezone    string
}
```

Caveats:

- `*ExtendedUser ≠ *authapi.User` — type identity is invariant in Go
- ent does not see new fields — module schema is sealed; sidecar table
  needed for typed DB columns
- mod-auth's API still returns base `User` — host service wraps **after**
  the call
- Cannot pass `*ExtendedUser` where `*authapi.User` is expected; pass
  `eu.User` instead
- JSON marshals flat for anonymous embedding (good for GraphQL); nested
  for named embedding

**Three flavors:**

- Anonymous (`authapi.User`) — fields promoted, JSON flat ✅ default
- Named (`User authapi.User`) — explicit, JSON nested
- Pointer (`*authapi.User`) — for shared instances

**Already implemented in repo:** `saas/pkg/users/service.go` has
`EnrichedUser` with anonymous embedding of `authapi.User`. The
"extension" is wrap + add, not mutate.

**This generalizes to a rule:**

> A module's struct can be wrapped, never extended. The wrapping happens
> at HOST (composition layer). The original struct stays sealed.

### 20. Rust comparison

**Question:** how does struct extension work in Rust?

**Answer:**

Same fundamental limit as Go (cannot inject fields into external crate's
struct), but with three ergonomic wins:

- **Extension traits** — `impl UserExt for mod_auth::User { ... }` adds
  methods to a foreign type. Go has no equivalent.
- **Newtype + `Deref`** — wrapping struct with `impl Deref` gives implicit
  coercion: `&ExtendedUser` → `&User` automatically. Go needs explicit
  `eu.User`.
- **Macros** — `#[derive(Deref)]` from `derive_more` generates wrap
  boilerplate. Go has no macros.

**ORM constraint identical:** SeaORM/Diesel, like ent, codegen schema.
Cannot add columns from outside crate. Sidecar table pattern applies.

**Implication for V2 architecture:** if ever ported to Rust, the shape
holds — modkit-as-trait-crate, per-module crates, soft FK, host
composition. Only the friction at wrapping boundaries reduces. Capability
modules become trait crates (`mod-auth-phone` ships `HasPhone` trait).


### 21. Template/scaffold model alternative

**Question:** what if mod-auth ships as a downloadable template that the
consumer scaffolds into `modules/mod-auth/`, then customizes locally?

**Two distribution models compared:**

| aspect | winner |
|---|---|
| schema-level customization | template |
| phone-or-no-phone variations | template |
| upstream bug fix flow | module |
| security patches auto-flow | module |
| type unification across consumers | module |
| many consumers / framework distribution | module |
| single team / heavily custom shape | template |
| public starter kit | template |

**Recommended hybrid:** template the SHELL (schema, config, bindings),
module the CORE (validation, hashing, JWT, generic logic).

```
Layer 1: modkit                  ← Go module (interfaces only)
Layer 2: mod-auth-core           ← Go module (logic + validation)
Layer 3: modules/mod-auth/       ← TEMPLATE-scaffolded into consumer
```

Schema customization happens locally in Layer 3. Generic logic flows
upstream via `go get -u` from Layer 2.

**Implementation:** ~300 LOC `modkit-cli scaffold` using stdlib
`text/template`. `modtemplate.yaml` declares parameters; `_template/`
tree contains `.tmpl` files. Walk + render + run post-hooks (entg,
go mod tidy).

**Hard problem deferred:** re-scaffold (apply upstream template changes
to already-customized scaffold). Most tools (`cargo generate`,
`cookiecutter`) punt. Acceptable for now — diff and merge manually.

**Implication for V2:** existing `modules/mod-auth` could become the
canonical template. Keep dual-mode: works as Go module today, has
template variant for consumers who want full customization.

This gives a 4-tier final stack:

| tier | content | distribution |
|---|---|---|
| Layer 1: modkit | interfaces only | Go module |
| Layer 2: mod-*-core | logic, hashing, validation | Go module |
| Layer 3: modules/mod-* | schema, bindings | scaffolded template |
| Layer 4: host | composition, sidecar, lifecycle | consumer code |

Capability modules (mod-auth-phone) collapse to scaffold flags
(`--with=phone`). Configurable fields problem dissolves.


### 22. Language comparison for type extension

**Question:** which language supports type extension or is most flexible?

**Tier ranking:**

- **S — runtime open classes:** Ruby, Python, JavaScript. Add fields,
  methods, anything, anywhere. Dynamic typing tax.
- **A — typed extensions (methods + computed props):** Swift, Kotlin,
  Scala 3. Best balance for typed languages. No stored fields though.
- **B — limited extension:** C# (partial classes within asm), TypeScript
  (declaration merging, typing only), Rust (ext traits + Deref), Dart.
- **C — sealed:** Go (embedding only), Java (inheritance only).

**Cannot add stored fields to external type in ANY mainstream typed
language.** Only dynamic languages (Ruby, Python, JS) can do this at
runtime. Memory layout reasons.

**Special case — ORM schema customization:**

Ruby + Rails wins by miles. ActiveRecord introspects DB schema at boot.
Adding a migration = adding a field on the model class instantly. No
codegen, no sidecar, no contract maintenance.

For typed languages: all face the same ORM constraint as Go's ent —
schema is code, sealed at compile time. Sidecar tables are universal
workaround.

**Application to V2:**

Architecture decisions (modkit, per-module api/, soft FK, sidecar,
capability modules) are language-independent. Only friction at
boundaries changes:

| boundary | go | rust | swift | kotlin | ruby |
|---|---|---|---|---|---|
| ORM schema customization | extreme | extreme | high | high | low |
| add methods to external type | medium | low | low | low | low |
| wrap with promoted access | medium | low (Deref) | low | medium | low |
| "add phone unique" customization | extreme | extreme | extreme | extreme | low |

**Verdict for current V2:** stay with Go + template scaffold hybrid
(Turn 26). Gets ~80% of Ruby's customization DX while keeping Go's type
safety + perf. Best deal Go can offer for the boilerplate's mixed
constraints.

**Would only switch language if:** starting fresh AND consumer schema
customization is the #1 priority AND team open to dynamic typing.
Then Ruby + Rails. Otherwise Go's tax is bearable.


### 23. Swift type extension deep dive

**Question:** how does type extension work in Swift?

**Answer:**

Swift `extension` keyword can add 6 things to any type (own or external):

1. Computed properties (instance + static)
2. Methods (instance + static)
3. Initializers (extra inits)
4. Subscripts
5. Nested types
6. Protocol conformances (retroactive allowed — Rust orphan-rule analog
   absent)

**Cannot add:** stored properties (same hard limit as all typed
languages — memory layout is fixed).

**Killer feature:** protocol extensions = default method implementations
shared across all conformers. Closest typed-language equivalent to Ruby's
mixin/module pattern.

**Cross-module:** extending stdlib types or third-party types is
trivial. Just `import ModAuth; extension User { ... }`. No orphan rule
restriction (Swift trades safety for flexibility vs Rust here).

**Application to V2 architecture:**

If V2 rewritten in Swift:

```swift
extension ModAuth.User {
    var phone: String? { Sidecar.phone(for: self.id) }
    var displayName: String { "\(firstName) \(lastName)" }
}
```

`users.Service.EnrichedUser` (current Go pattern) collapses to
`extension User`. Caller-side feels native — no wrapping type visible
in API.

**But ORM constraint identical:** Vapor's Fluent / CoreData seal schemas
at module boundary like ent. Sidecar tables still needed. Swift solves
read-side ergonomics, not DB schema customization.

**Verdict:** Swift would reduce host-composition friction by ~50%. Schema
extension friction unchanged. Architecture decisions (modkit, per-module
api/, soft FK, sidecar, capability modules) all still apply. Same shape,
nicer surface.


### 24. Swift vs Go performance

**Question:** which is faster for backend?

**Verdict for V2: Go.**

| dimension | verdict |
|---|---|
| HTTP throughput (10K+ rps) | go (decisive) |
| single-thread CPU | tie (within 10-15%) |
| compile times | go (massive — Swift slow) |
| memory footprint | tie |
| GC pauses | swift (ARC deterministic) |
| backend ecosystem | go (much larger) |
| concurrency model | go (goroutines beat tasks) |
| type extension ergonomics | swift |
| schema customization | tie (same ORM constraint) |
| overall for boilerplate | go |

**Concurrency is the deciding factor.** Goroutines (~2KB per task,
M:N scheduler, mature) outperform Swift Tasks (heavier, cooperative
threads, younger runtime) by 2-3x at HTTP scale.

**Compile-time win for Go is huge.** Small project: 1-3s vs 30-60s.
Medium: 5-15s vs 3-10 minutes. Affects dev velocity dramatically.

**Swift wins** isolated CPU benchmarks (fibonacci, sorting) due to
LLVM + value-types + ARC. Doesn't translate to backend dominance —
real workloads dominated by I/O wait + allocation churn + concurrency.

**Where Swift would help V2:**

- Type extensions collapse `users.Service.EnrichedUser` to
  `extension User`
- No GC = predictable latency
- Sum types + protocols for domain modeling

**Where it would hurt V2:**

- 2-3x lower HTTP throughput at scale
- 10-100x slower compile (dev iteration pain)
- Smaller backend lib ecosystem
- More deploy surface (Linux Swift runtime less mature than Go static binary)

**Verdict:** stay with Go for V2. Swift is a major rewrite for marginal
architectural ergonomic wins. Only switch if iOS code-sharing is the
priority OR latency is critical (no-GC requirement) OR domain logic is
extremely type-heavy.

### 28. Hybrid clarification — Layer 2 is entity-agnostic

**Question:** how does the core lib consume entities when they aren't
generated yet (because they live in scaffolded Layer 3)?

**Answer:** core doesn't consume entities. Layer 2 ships pure functions
on primitives only. Layer 3 (scaffolded) is the bridge.

```
Layer 2 (core lib):     "Does generic things to strings."
                          - HashPassword(plain, cost)
                          - VerifyPassword(plain, hash)
                          - SignJWT(claims, secret, ttl)
                          - ValidateEmail(s)
                          - GenerateRandomToken()

Layer 3 (scaffolded):   "Has entities. Calls Layer 2 with extracted strings."
                          - schema/user.go (ent schema, customizable)
                          - module.go (extracts primitives, calls L2, writes entity)
```

**Real-world precedent:** bcrypt, jwt-go, uuid, validator, casbin —
all ship as Go modules without knowing your domain. They take strings/
maps/bytes; your code wraps them.

**When entity-aware logic needed in Layer 2:** declare tiny interface
in L2; L3 implements with ent.

```go
// Layer 2
type AttemptStore interface {
    Get(ctx, key) (count int, err error)
    Increment(ctx, key, ttl)
}
func CheckRateLimit(ctx, store AttemptStore, id, max) error { ... }

// Layer 3
type entAttemptStore struct{ client *ent.Client }
func (s entAttemptStore) Get(...) {...}
```

**Rule:** Layer 2 is logic. Layer 3 is state. No exceptions.

**Mental model:**

```
entity (L3) → extract primitives → L2 pure fn → primitives → write entity (L3)
```


### 29. Real-Go-code "template" pattern (no text templates)

**User constraint:** text-template `.tmpl` files are hard to debug/test.
Want the "template" to be real working Go code, and the extension to
ALSO be real Go code that extends the base.

**Resolution:** three Go patterns combined replace text-template scaffolds:

**Pattern 1 — Behavior iface + DefaultBehavior + consumer embeds:**

```go
// base — real code
type Behavior interface { HashPassword(...), ValidatePassword(...), ... }
type DefaultBehavior struct{}    // working impl
// methods on DefaultBehavior implement Behavior

// consumer — real code
type MyBehavior struct{ authbase.DefaultBehavior }   // embed
func (MyBehavior) ValidatePassword(...) error { /* override */ }
```

**Pattern 2 — Generics over entity type:**

```go
type Store[U any] interface { Create(...) (U, error); ... }
type Module[U any] struct { ... }

// consumer's MyUser type, consumer's Store[MyUser] impl
auth := authbase.New[MyUser](MyBehavior{}, myStore{client})
```

**Pattern 3 — Middleware chain for cross-cutting:**

```go
type CreateMiddleware[U any] func(next CreateFn[U]) CreateFn[U]

// consumer wraps with real Go functions
auth := authbase.New[MyUser](MyBehavior{}, myStore{},
    RateLimitMiddleware(rl), AuditMiddleware(audit),
)
```

**Real-world precedents:** net/http, database/sql, io.Reader, gorilla/sessions,
casbin, jwt-go all use this pattern. None use template engines.

**Vs templates:** real-code wins debugging, IDE support, type safety,
testing, upstream updates. Templates only win for "dozens of flags
vary every line" — rarely modules.

**Application to V2:**

This becomes a refinement of Approach 5 (Hybrid scaffold + core). Drop
the scaffold step. Layer 2 ships real code with extension points.
Layer 3 (consumer's app) is real Go code that imports + extends.

```
Layer 2 (mod-auth-base):  Behavior iface + DefaultBehavior + Store[U] iface
                          + Module[U] generic + middleware types
                          + pure helpers (HashPassword, SignJWT, etc)

Layer 3 (consumer's app): MyBehavior embeds DefaultBehavior + overrides
                          MyUser struct + Store[MyUser] impl
                          RateLimit/Audit/etc as Go fns
```

No `.tmpl`, no scaffolder, no codegen step. Just `go get` + write code.

**Migration from current V2:**

```
1. Extract Behavior + DefaultBehavior into mod-auth-base (Go module)
2. Generify Module → Module[U] with Store[U] iface
3. Consumer provides MyUser + Store[MyUser]
4. Add middleware support for create/login/etc
```


### 30. AST scaffolding locked as final extension mechanism

**Trigger:** user pointed out that all behavior/generics/middleware
patterns customize methods but not struct fields. For typed field
extension, codegen is unavoidable.

**Resolution:** AST-based code transformation via `mod-cli` tool using
`github.com/dave/dst`. Consumable module ships as REAL working Go;
extension config declares struct field additions / method body
replacements; tool reads AST, mutates, writes real Go to consumer's
`modules/mod-auth/`.

**Why AST won (over text templates):**

- Source ships as real working Go (compiles, tests pass standalone)
- Output is real Go (debuggable, testable in consumer's repo)
- No template engine to debug
- Fits Go ecosystem norms (wire/mockgen/protoc-gen-go pattern)
- Solves typed-field-on-entity-table without sidecars or jsonb

**Build status: locked architecturally, deferred operationally.**

Existing V2 modules require zero changes. AST tool can be built any time.

**Build trigger:** 2+ consumers need diverging schemas, OR routine
module copy-paste, OR selling boilerplate as a product.

**Phase 1 effort:** ~770 LOC Go (1-2 days focused work). Re-scaffold
support deferred to Phase 3 (hard problem, 3-way merge).

**Light hygiene to maintain meanwhile:**

- Field declarations in `field.String("name").Unique()` style (predictable for AST)
- Behavior methods on Module struct (easy receiver match)
- api/types.go as flat struct (easy field injection)
- One schema per file (tool addresses by filename)

**Artifacts:**

- `MISSION_V2_AST_PLAN.md` — full plan with examples, tool sketch, roadmap
- `MISSION_V2_DECISIONS.md` ADR-V2-013 — locks AST as the V2 customization mechanism

**Default plan:** keep shipping features on V2's current shape. Build
mod-cli the day a consumer's schema diverges from yours.


### 31. What V2 loses vs centralized dbent

**Question:** beyond SQL JOINs, what else does V2 give up?

**17 losses enumerated, ranked by severity:**

| loss | severity |
|---|---|
| Cross-module SQL JOINs | major |
| Cross-module ent edges + eager load | major |
| DB-level FK + ON DELETE CASCADE | major |
| Refactoring atomicity (rename column) | major |
| ent edge schemas (M2M with extra fields) | medium |
| Polymorphic edges | medium |
| ent hooks fire across modules | medium |
| ent privacy/authz cross-client | medium |
| entgql automatic bindings | medium |
| Global migrations in one tx | medium |
| Test fixtures with related entities | medium |
| ent optimistic locking across tables | minor |
| Bulk multi-table inserts via ent | minor |
| Compile-time FK type checking | minor |
| Single tracing root | minor |
| Schema-level cross-module mixins | minor |

**Mitigations already built into V2:**

- Reader.GetMany for batch fetching → mitigates JOIN loss
- WithTx + clientForCtx → cross-module atomic transactions
- Cascade orchestrator at host (UserDeleter) → app-level FK enforcement
- NATS events → reactive cross-module side effects
- DataLoader pattern at GraphQL → N+1 mitigation

**Future mitigations (build when triggered):**

- Optional host aggregated ent client → admin/reporting queries needing real JOIN
- Orphan detection sweeper → catches cascade misses
- DataLoader integration in apidash → when GraphQL hits module data

**Where pain still hurts:**

- Heavy analytics queries (5+ table JOINs) → mandatory aggregated client
- "Forgot a cascade hook" silent orphan accumulation → discipline + sweeper
- Cross-module refactoring → api.Reader contract stability is the line

**Tradeoff verdict:**

For distributable SaaS framework (multiple consumer projects):
**worth it.** Losses are price of portability. App-level cascade is
correct in code but fragile in operation; needs review discipline.

For single-team product on single monorepo: V2 is unnecessary
complexity over existing centralized dbent (Approach 3). Centralized
keeps all ent power, loses only portability.


### 32. Convex as alternative paradigm

**Question:** how does Convex handle the same pluggability concerns?

**Answer:** different stack entirely — TS reactive backend platform; eliminates V2's class of problems by switching paradigms.

**Key mechanisms:**

- Schema as TS code (no migrations) — extension = edit one file
- Functions as TS files in `convex/` dir
- Types auto-inferred end-to-end
- Real-time built-in (`useQuery` auto-subscribes)
- Convex Components: npm-installable modules with own namespaced schema + functions, composed via `convex.config.ts` `app.use(component)`

**vs V2:**

| Aspect | Convex | V2 |
|---|---|---|
| Distribution | npm install + app.use() | go.work + modkit |
| Schema namespacing | automatic | manual per-module ent |
| Cross-module queries | native (single backend) | service-layer batch + DataLoader |
| Schema customization | edit TS, types propagate | AST scaffold (deferred) |
| Codegen | none (inference) | ent + gqlgen + PKL |
| Real-time | built-in | manual (NATS) |
| Lock-in | Convex cloud | self-hostable PG |
| Language | TS only | Go |

**What it solves over V2:** schema extension trivial, no JOINs lost (cross-component native), real-time free, no codegen step.

**What it costs:** TS only, cloud-mostly, NoSQL, vendor lock, consumers must adopt Convex too.

**Verdict for boilerplate:** not a V2 replacement — different stack. Stay V2 for Go/PG/ent investment. Convex worth considering only if greenfield TS where real-time + customization flexibility > Go ecosystem value.
